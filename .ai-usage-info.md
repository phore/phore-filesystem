# AI Usage Info

## Version 2 / Plattform

Der hier beschriebene Security-Vertrag gehört zur neuen Major-Version `v2`. `phore/filesystem` v2 setzt PHP `>=8.5` voraus. Symlinks werden mit `followSymlinks=true` standardmäßig wie im normalen Dateisystem aufgelöst; bei gesetztem `rootDir` darf das aufgelöste Ziel die Root nicht verlassen. Für eine explizite No-Symlink-Policy wird `followSymlinks=false` gesetzt.

## Sinn der Library

`phore/filesystem` ist die zentrale Dateisystem-Abstraktion für Phore-basierte Libraries und Anwendungen. Sie kapselt Pfade, Dateien, Verzeichnisse, Temp-Dateien und Streams in `PhoreUri`, `PhoreFile`, `PhoreDirectory`, `PhoreTempFile` und `PhoreTempDir`.

**Sicherheitsrelevante Dateisystemprüfungen gehören hierher.** Konsumierende Libraries sollen nicht selbst Symlink-Prüfungen, Root-Grenzen, Existenz-/Lesbarkeitsguards, rekursive Walk-Sicherheitslogik oder parallele Exception-Hierarchien nachbauen. Sie binden die benötigten Restrictions einmal am Phore-Einstieg und verwenden danach die normalen Datei-/Directory-Operationen.

Die High-Level-Methoden wie `set_contents()`, `append_content()` und `get_contents()` arbeiten weiterhin mit File-Locking. Sicherheits-Restrictions werden zusätzlich von allen daraus abgeleiteten Phore-Objekten geerbt.

## Direkte Dateioperationen und Fehlerweitergabe

Im Normalfall direkt `phore_file($path)->get_contents()`, `get_yaml()`, `get_json()`, `get_front_matter()` oder die entsprechende Directory-Operation aufrufen. Keine vorgeschalteten `file_exists()`-/`is_readable()`-Guards, keine privaten `readFile()`-/Walk-Wrapper und kein pauschales Catch-and-Re-throw mit einer allgemeineren Exception. Phore prüft die Voraussetzungen an der verantwortlichen Abstraktionsgrenze und liefert Dateikontext in der Exception.

Explizite fachliche Voraussetzungen werden mit `assertFile()`, `assertDirectory()`, `assertReadable()`, `assertWritable()`, `assertNoSymlinks()`, `assertRelativePath()` und `assertFileTarget()` ausgedrückt. `asFile()` und `asDirectory()` ändern nur die Sicht auf denselben Pfad; sie bestätigen keine Existenz. Exceptions werden normalerweise bis zur Anwendung durchgereicht. Ein Catch ist für eine tatsächliche Behandlung wie einen definierten Fallback oder Retry gedacht, nicht zum Umbenennen desselben Fehlers.

## FilesystemOptions und Restrictions

`phore_uri()`, `phore_file()` und `phore_dir()` akzeptieren als zweites Argument ein Assoc-Array, ein `FilesystemOptions`-Objekt oder `null`. Arrays werden strikt validiert; unbekannte Keys und lose Typen wie `'false'` für einen booleschen Wert werden abgelehnt.

Zulässige Keys:

- `rootDir: string|null` — begrenzt alle Zugriffe auf diesen Verzeichnisbaum; Default bei einem neuen String-Einstieg: `null`.
- `followSymlinks: bool` — Default `true`; Symlinks werden normal aufgelöst, dürfen bei gesetztem `rootDir` aber nicht aus der Root herausführen. `false` verbietet Symlinks vollständig.
- `allowHardLinks: bool` — Default `true`; `false` lehnt reguläre Dateien mit mehreren Hardlinks ab.
- `requireAtomicContainment: bool` — Default `false`; `true` verlangt ein atomar absicherndes Backend. Solange kein solches Backend verfügbar ist, schlägt die Operation fail-closed mit `UnsupportedFilesystemPolicyException` fehl.

Beispiel:

```php
$docs = phore_dir('/srv/site/docs', [
    'rootDir' => '/srv/site/docs',
]);

$config = $docs->withSubPath('.shiller.yml')->asFile()->get_yaml();
```

Bei einem bereits gebundenen Phore-Objekt bedeuten fehlende Options, `null` und `[]` **Vererbung**, nicht Default-Reset. Ein partielles Array ändert ausschließlich ausdrücklich vorhandene Keys. Ein vollständiges `FilesystemOptions`-Objekt ist ein vollständiger Snapshot. Restrictions dürfen bei einer Ableitung nur gleich bleiben oder strenger werden: eine bestehende Root darf nicht auf `null` gesetzt oder erweitert, `followSymlinks=false` nicht auf `true` gelockert, `allowHardLinks=false` nicht aufgehoben und `requireAtomicContainment=true` nicht abgeschaltet werden. Eine solche Rechteausweitung wirft `FilesystemPolicyViolationException`.

**Strings verlieren den gebundenen Sicherheitskontext.** `(string) $file` und `getUri()` sind nur Pfaddarstellungen. Innerhalb einer Library deshalb Phore-Objekte weiterreichen und nicht aus deren Strings neue unbeschränkte Objekte rekonstruieren. Factory-Casts, `asFile()`, `asDirectory()`, Pfadableitungen, Assertions, Walk-Ergebnisse und Streams behalten dagegen den Context.

## Walk und relative Basis

`genWalk()`, `walk()`, `walkR()`, `list()`, `listFiles()` und `getListSorted()` verwenden denselben Traversierungsvertrag. Sicherheitsprüfung und Directory-Rekursion erfolgen vor dem Ergebnisfilter; ein nicht passender Symlink oder ein Zugriffsfehler wird deshalb nicht durch `*.md` oder einen anderen Filter versteckt.

Für einen vollständigen, deterministischen Datei-Scan:

```php
foreach ($root->listFiles('*.md', recursive: true, sort: 'path') as $file) {
    $relative = $file->getRelPath($root);
    $contents[$relative] = $file->get_contents();
}
```

`sort: 'path'` sortiert die vollständig materialisierte Dateiliste global nach dem relativen Pfad. `getRelPath($base)` ändert nur die Darstellung, niemals `rootDir` oder andere Restrictions. Ein rekursiver Lauf, der sein `recursionLimit` überschreiten müsste, wirft statt eine still unvollständige Liste zurückzugeben.

## Sicherheitsgrenze und Fail-closed-Verhalten

Diese Library ist gerade dafür vorgesehen, sicherheitsrelevante Dateisystementscheidungen zentral zu treffen. Wenn eine Root-Zuordnung, Link-Auflösung, Dateityp-Prüfung oder Backend-Fähigkeit nicht sicher bestimmt werden kann, wird lieber eine Exception mehr geworfen als mit schwächeren Regeln weitergearbeitet. Es gibt keinen Fallback von einer fehlgeschlagenen sicheren Operation auf einen unbeschränkten String-Zugriff.

`rootDir` ohne `requireAtomicContainment` schützt nicht gegen einen Angreifer, der den Dateibaum gleichzeitig zwischen Prüfung und Zugriff verändert. Die aktuelle Implementierung lehnt `requireAtomicContainment=true` deshalb ab, statt eine nicht vorhandene atomare Garantie vorzutäuschen. Rohe Ressourcenexporte sind für root-gebundene Streams ebenfalls gesperrt.

## Verbindliche Agentenregel bei Library- oder Sicherheitsfehlern

Findet ein Agent beim Entwickeln eines Consumers einen Fehler, eine Mehrdeutigkeit mit möglicher Fehlfunktion oder insbesondere einen möglichen Sicherheitsfehler in `phore/filesystem`, darf er diesen **nicht** mit zusätzlichen Consumer-Guards, Catch-Logik, kopierter Pfadprüfung oder einem anderen Workaround verdecken. Die weitere Implementierung der betroffenen konsumierenden Funktion ist abzubrechen und der Nutzer ist über den konkreten Befund und die mögliche Auswirkung zu informieren. Die Korrektur gehört in diese Library und ist als reviewbarer Pull Request hier zu erstellen beziehungsweise vorzuschlagen. Erst nachdem der Nutzer die Library-Korrektur oder den vorgeschlagenen Umgang ausdrücklich bestätigt hat, darf die davon abhängige Consumer-Implementierung weitergeführt werden.

Dasselbe Prinzip gilt umgekehrt beim Entwickeln dieser Library: Wird ein Sicherheitsfehler in der zentralen Prüfung gefunden, wird er hier behoben und mit Security-Regressionstests abgesichert; Consumern wird keine abweichende Ersatzlogik empfohlen.
